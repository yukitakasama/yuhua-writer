## 1. 阶段目标与边界

### 1.1 第一阶段**要做**的

写作软件的最小完整闭环：**建书 → 建卷章 → 写字 → 存住 → 找得到 → 交得出去**。

1. 工作区的新建 / 打开 / 最近列表
2. 书 → 卷 → 章 三级结构的完整增删改与拖拽排序
3. 编辑器：Markdown 即时渲染、自动保存、撤销重做、查找替换、快捷键
4. 大纲视图与章节摘要
5. 字数统计与写作目标
6. 跨章节全文检索（中文可用）
7. 外观体系：主题、排版参数、**字体自由选择**、专注模式
8. **导出引擎：TXT / Markdown / HTML / DOCX / PDF / EPUB**
9. **写作统计：码字日历、写作记录、年热力图、连续天数**
10. 数据安全：原子写、自动备份、回收站、索引重建
11. 云盘工作区兼容（不自建同步服务，见 4.5 节）

### 1.2 第一阶段**明确不做**的

- 自建云同步服务、账号体系、多设备实时协作（见 4.5 节替代方案）
- 实时协作、评论、审阅
- 插件系统、脚本扩展
- AI 辅助写作 / 续写 / 校对
- 富文本（Word 式）与块编辑器（Notion 式）形态
- **多语言界面（i18n）** —— 本阶段仅中文，但文案集中管理
- **LaTeX / 公式排版、复杂表格的精细导出**
- 移动端的触屏交互深度优化（仅保留可构建的骨架）
- 官网、社区、插件市场
- **应用图标的最终设计**（本阶段使用占位图标，用户后续自行设计）

### 1.3 「能用」的定义

一个网文作者可以**只用这个软件**完成一天的更新：打开即写、不用手动保存、断电不丢稿、想找某段能搜到、能看到自己这一个月的码字曲线、写完能按平台要求导出交稿。达不到这条，第一阶段不算完成。

## 2. 技术选型与理由

### 2.1 选型总表

| 层 | 选型 | 选它的理由 | 被否决的方案与原因 |
| --- | --- | --- | --- |
| 应用框架 | **Tauri 2** | 复用系统 WebView，不打包 Chromium；安装包 5–10 MB 级；Rust 内核内存可控；官方支持 Win / macOS / Linux / Android / iOS | **Electron**：每个进程基线 100 MB+，直接违背要求②；**Flutter**：需自绘引擎，桌面文本编辑与中文 IME 生态弱，且本机未安装 |
| 前端框架 | **SolidJS** | 无虚拟 DOM、细粒度更新，每次按键的更新开销恒定且极小；运行时约 7 KB | **React**：VDOM diff + 调度器在长文档高频输入下产生额外分配；**Vue**：运行时更重 |
| 语言 | **TypeScript（strict）+ Rust 2024 edition** | 类型贯穿前后端，编译期拦截接口漂移 | 纯 JS：无类型约束 |
| 构建 | **Vite** | 极快 HMR；产物按路由 / 功能分包，支持动态 import 懒加载 | Webpack：冷启动与内存开销更大 |
| 编辑器内核 | **CodeMirror 6** | 模块化 tree-shaking；**视口渲染**（内存与文档长度无关）；原生支持中文 IME 与装饰替换 | **自研 contenteditable**：IME / 撤销 / 选区的坑极深；**Monaco**：体积大、面向代码非写作；**ProseMirror**：富文本文档模型，与「Markdown 文件为真源」冲突 |
| 索引 / 检索 | **SQLite + rusqlite（bundled feature）+ FTS5**，中文用自研二元组分词器 | 零系统依赖、单文件、可静态编译 | **Tantivy**：索引体积与常驻内存更高（备用方案） |
| 文件监听 | **notify** | 跨平台成熟，处理外部编辑器与云盘同步带来的改动 | 轮询：违背要求② |
| IPC 类型 | **tauri-specta** | 由 Rust 命令签名生成 TS 类型，杜绝接口漂移 | 手写类型：必然漂移 |
| 内置字体 | **思源宋体 SC + 霞鹜文楷**，WOFF2 子集化内置，FontFace API 懒加载 | 离线可用、排版一致；子集化把 20 MB+ 压到约 2.5–3 MB/字重 | 全量内置：单字重 20–24 MB，不可接受；在线加载：违背离线优先 |
| **导出引擎** | **纯 Rust，单一 IR + 六渲染器**（见第 9 章） | 不整书进内存；产物确定、可测试；避免引入重型 JS 导出库 | JS 侧导出：需 pdfmake/docx.js 等重型依赖，违背要求② |
| 动效 | **CSS 过渡 + Web Animations API + 自研轻量弹簧（约 1 KB）** | 只驱动 `transform/opacity`，走合成器 | **Framer Motion / GSAP**：运行时体积与每帧分配不符合要求② |
| 图标与图表 | **手写 SVG 组件 + 纯 SVG 自绘图表** | 零字体文件、零外链、可 tree-shake、随 `currentColor` 变色 | 图标字体 / 图表库（ECharts 等）：体积与内存开销大 |
| 状态管理 | **Solid 原生 signal / store** | 无全局状态树快照、无不可变复制 | Redux 类：内存与样板开销 |
| 测试 | `cargo test` / `vitest` / `tauri-driver` | 与选型配套，端到端可跑真实窗口 | — |
| CI/CD | **GitHub Actions + tauri-action** | 官方矩阵构建；同时作为字体完整包的发布通道 | — |

### 2.2 为什么 Tauri 2 是关键决策

要求②「内存占用率必须控制在最低」直接决定了框架选择：

- Electron 无论应用多小，都要为 Chromium 付固定成本（通常 100–200 MB 常驻）
- Tauri 复用系统 WebView：Windows 用 WebView2、macOS 用 WKWebView、Linux 用 WebKitGTK
- Rust 内核只做文件 IO、索引、检索、导出，无 GC、无运行时，空闲时内存曲线是平的

### 2.3 WebView2 分发策略（v1.2 确定：不捆绑）

Tauri 在 Windows 上有若干 `webviewInstallMode`。我们**明确选择不捆绑**：

| 方案 | 体积代价 | 决策 |
| --- | --- | --- |
| `embedBootstrapper` | +1.8 MB | 未选 |
| `offlineInstaller` | **+127 MB** | 明确否决 |
| `downloadBootstrapper` | 几乎为 0（运行时下载约 1.8 MB 引导器） | **采用** |
| `skip` | 0 | 作为兜底，配合自研提示 |

**采用 `downloadBootstrapper`**，理由与后果：

- WebView2 Evergreen 运行时自 Windows 11 起预装；Windows 10 自 2021 年起随 Edge 更新广泛铺开，**绝大多数目标用户已具备**
- 不捆绑让安装包保持在 25 MB 级（体积全部留给字体），符合要求②
- **代价**：极少数无运行时的机器（如长期离线、精简版系统）首次启动需联网补装

**必须配套的兜底**（不能只依赖运行时下载）：

1. 启动探测：Rust 侧在创建窗口前检测 WebView2 是否可用
2. 缺失时显示**原生对话框**（不依赖 WebView，因为此时 WebView 不可用）：
   - 说明需要 Microsoft Edge WebView2 运行时
   - 提供「打开下载页面」与「退出」两个选项
   - 文案说明这是系统的免费组件，不是本软件额外要求
3. 文档中在「安装」章节显式列出该前置条件

**支持范围**：Windows 10 1809 及以上（64 位）。不承诺 Windows 7/8。

## 3. 系统架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────────┐
│  表现层  SolidJS + CodeMirror 6 + 内置字体（FontFace 懒加载）│

│  原则：薄壳，不含业务逻辑                                  │

┌────────────────────────┴─────────────────────────────────┐
│  领域层  crates/                                          │
│  ├─ yuhua-core     Book / Volume / Chapter 模型与不变量     │
│  ├─ yuhua-fs       原子写、备份、回收站、文件监听            │
│  ├─ yuhua-store    SQLite 表、FTS5、增量索引、检索           │
│  ├─ yuhua-export   导出 IR + 六格式渲染器                   │
│  └─ yuhua-stats    码字记录、日历、热力图数据与合并           │
└────────────────────────┬─────────────────────────────────┘
                         │ std::fs / rusqlite / zip
┌────────────────────────┴─────────────────────────────────┐
│  持久层                                                    │
│  ├─ 工作区目录：Markdown（真源）+ .yuhua/（配置/备份/统计）  │
│  └─ 系统应用数据目录：index/<workspace-id>.sqlite（缓存）    │
└──────────────────────────────────────────────────────────┘
```

### 3.2 五条不可违反的不变量

1. **文件是真源，索引是缓存。** 删除索引库后应用必须能完全重建，且用户无感。
2. **写入必须原子。** 任何时刻断电，磁盘上要么是旧内容、要么是新内容，不允许半截文件。
3. **索引库不进工作区。** 二进制数据库放系统应用数据目录，避免云盘损坏。
4. **UI 线程不做重活。** 所有文件 IO、检索、导出都在 Rust 侧异步执行。
5. **导出不整书载入内存。** 导出按章流式处理，内存峰值与书籍总字数无关。

- 正文是**用户能直接用任何编辑器打开**的 `.md` 文件

- **工作区内只有文本与 JSON，没有任何二进制** —— 云盘同步安全的前提

- Front Matter 是元数据的**真源**；SQLite 只是它的缓存
- 缺失字段一律给默认值，不因为用户删了某行就报错

### 4.3 SQLite 表结构与存放位置

**存放位置**：索引库**不放在工作区里**，放在系统应用数据目录：

| 平台 | 路径 |
| --- | --- |
| Windows | `%APPDATA%\YuhuaWriter\index\<workspace-id>.sqlite` |
| macOS | `~/Library/Application Support/YuhuaWriter/index/<workspace-id>.sqlite` |
| Linux | `~/.local/share/YuhuaWriter/index/<workspace-id>.sqlite` |

原因：SQLite 是二进制且带 WAL 与共享内存文件，云盘客户端对正在写入的二进制文件做部分同步极易损坏。而索引**本来就是可抛弃的缓存**。

```sql
CREATE TABLE books (
  id TEXT PRIMARY KEY, title TEXT NOT NULL, root TEXT NOT NULL,
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL
);

CREATE TABLE volumes (
  id TEXT PRIMARY KEY,
  book_id TEXT NOT NULL REFERENCES books(id) ON DELETE CASCADE,
  title TEXT NOT NULL, sort INTEGER NOT NULL
);

CREATE TABLE chapters (
  id TEXT PRIMARY KEY,
  book_id TEXT NOT NULL REFERENCES books(id) ON DELETE CASCADE,
  volume_id TEXT REFERENCES volumes(id) ON DELETE CASCADE,
  path TEXT NOT NULL UNIQUE, title TEXT NOT NULL, sort INTEGER NOT NULL,
  status TEXT NOT NULL DEFAULT 'draft',
  word_count INTEGER NOT NULL DEFAULT 0,
  mtime INTEGER NOT NULL, content_hash TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);

-- 全文检索：外部内容表模式，正文不重复存储
CREATE VIRTUAL TABLE chapters_fts USING fts5(
  title, body, content='', tokenize='yuhua_bigram'
);
```

**中文分词方案**：FTS5 默认分词器对中文按空白切分，完全不可用。方案是**自研二元组（bigram）分词器**，通过 `rusqlite` 注册自定义 FTS5 tokenizer：

- 中日韩字符按相邻二字切分（「羽化写作」→ 羽化 / 化写 / 写作）
- ASCII 字母数字按词切分并转小写
- 单字查询退化为前缀匹配
- **备用方案**：若误召回明显，引入 `jieba-rs` 做词级切分

### 4.4 写入与恢复

| 机制 | 做法 | 解决的问题 |
| --- | --- | --- |
| 原子写 | 写 `.tmp` → `fsync` → `rename` 覆盖 | 断电只可能丢最后一次未完成写入 |
| 防抖保存 | 停止输入 800 ms 后保存；失焦、切章、关窗前强制保存 | 减少磁盘写入，兼顾不丢稿 |
| 轮转备份 | 保存前若距上次快照 > 5 分钟，旧版存入 `.yuhua/backup/`，保留最近 20 份 | 误删、误改写可回溯 |
| 崩溃日志 | 保存前写待提交记录，成功后清除 | 崩溃后可提示恢复 |
| 回收站 | 删除即移动到 `.trash/`，保留 30 天 | 误删可救 |
| 索引重建 | 一键从 Markdown 重建 SQLite | 索引损坏或换机时零损失 |

### 4.5 无服务器下的同步策略

已确认：**没有自建云同步服务，因为没有服务器**。方案是「**工作区就是一堆纯文本文件，把它放进用户已有的云盘**」。

支持目标（用户自选，软件不做绑定）：坚果云 / 阿里云盘 / 百度网盘、OneDrive / Dropbox / Google Drive / iCloud Drive、Syncthing / 局域网共享 / U 盘、Git。

**软件为此做的三件事：**

1. **工作区零二进制**（4.1 / 4.3 已落地）：索引库移出工作区
2. **优雅处理外部改动**：`notify` 监听云盘落盘事件，自动重载未在编辑的章节；正在编辑的章节若被外部改动，弹出冲突提示，**保留内存版本并另存冲突副本，绝不静默覆盖**
3. **识别冲突副本**：识别「xxx (冲突副本 2026-01-01).md」这类命名，在 UI 中提示「发现 N 个冲突文件」，引导逐条对比，**绝不自动删除**

**统计数据的合并**：写作统计（第 10 章）也在工作区里，会被同步。采用**单调合并**策略，冲突不丢数据（见 10.4 节）。

**能力边界（写进用户文档）：**

- 提供的是**最终一致性同步**，不是实时协同
- 同一时间只建议一台设备编辑；同时改同一章会产生冲突副本，需人工合并
- 冲突由云盘决定，软件只能事后识别与提示

## 5. 设计语言与动效系统（要求 ①）

### 5.1 视觉原则

1. **内容优先**：写作时屏幕上只有字。常驻 UI 用极低对比度退到背景。
2. **克制的层级**：一个中性色阶 + 一个强调色。层级靠 1px 描边与极轻阴影。
3. **无装饰性元素**：不加渐变滥用、不加拟物质感。每个像素都要有理由。
4. **排版是主角**：正文区最大宽度默认 720 px（可调 560–960），行高 1.8，默认段间距。
5. **零 emoji、零图标字体、零外链图片**（见第 7 章）。

### 5.2 设计令牌

/* 圆角 */
--r-sm: 4px; --r-md: 6px; --r-lg: 10px; --r-full: 999px;

/* 字体族（用户可覆盖；缺字自动回退系统字体，见 7.5）
   三个作用域：正文 / 标题 / 界面，各自独立可选 */

### 5.3 动效令牌

```css
--d-instant: 80ms;   /* 按压反馈 */
--d-fast:    120ms;  /* 悬停、焦点、开关 */
--d-base:    180ms;  /* 弹层、面板、列表项进出 */
--d-slow:    240ms;  /* 页面切换、抽屉 */
--d-page:    320ms;  /* 首次进入、大范围布局变化 */

--e-standard:   cubic-bezier(0.2, 0, 0, 1);
--e-decelerate: cubic-bezier(0, 0, 0, 1);
--e-accelerate: cubic-bezier(0.3, 0, 1, 1);

--spring-soft:  { stiffness: 300, damping: 30 };
--spring-snappy:{ stiffness: 500, damping: 35 };
```

### 5.4 性能铁律

> **只动画 `transform` 与 `opacity`。永不动画 `width / height / top / left / margin / box-shadow / filter`。**

补充规则：

- 动效元素临时加 `will-change: transform`，动画结束**必须移除**
- 同时运行的动效元素数量上限约 30，超出降级为直接切换
- 长列表滚动时暂停非可视区的入场动效
- **字体切换不得触发整页重排动画**：只更新 CSS 变量
- **热力图渲染不得逐格做动效**：365 个格子同时动画会直接违反要求②，只允许整体淡入一次

### 5.5 逐操作动效清单

| 交互 | 动效 | 时长 / 曲线 |
| --- | --- | --- |
| 按钮悬停 | 背景色过渡 | 120 ms / standard |
| 按钮按下 | `scale(0.97)` 回弹 | 80 ms 按下，弹簧回弹 |
| 侧栏折叠 / 展开 | 列宽过渡 + 内容 `opacity` 与 `translateX` | 240 ms / spring-soft |
| 章节切换 | 正文 `opacity` 0→1 + `translateY(4px→0)` | 180 ms / decelerate |
| 卷章树拖拽 | 被拖项跟随指针，其余项 FLIP 让位 | 实时，落位 spring-snappy |

| 删除章节 | 收缩 + 淡出，其余项上移 | 180 ms / accelerate |
| 保存状态指示 | 圆点缩放脉冲 → 静止 | 180 ms |
| 字数变化 | 数字滚动（roll）进位 | 120 ms |
| 命令面板 / 弹窗 | `scale(0.96→1)` + `opacity` | 180 ms / spring-soft |
| 弹层关闭 | `opacity` 1→0 + `scale(1→0.98)` | 120 ms / accelerate |
| Toast 进出 | `translateY` + `opacity` | 180 ms / spring-soft |
| 主题切换 | 全局颜色过渡（CSS 变量过渡） | 240 ms |
| 字体切换 | 仅更新 CSS 变量 + 缺字回退，不叠加位移动效 | 即时 |
| 检索结果跳转 | 目标段落滚动 + 高亮闪烁两次后淡出 | 320 ms |
| 空状态 | SVG 插画淡入 + 极低频呼吸动效 | 420 ms |
| 拖动分隔条 | 实时跟手 + 松手吸附 | 实时，吸附 spring-snappy |
| **导出进度** | 进度环推进 + 完成时对勾描边绘制 | 实时 / 完成 260 ms |
| **导出完成** | 结果卡片淡入 + 上移 | 180 ms / decelerate |
| **日历月份切换** | 网格交叉淡入 + 轻微 `translateX` | 200 ms / standard |
| **热力图首次渲染** | 整体 `opacity` 0→1，**逐格不动画** | 300 ms / decelerate |
| **热力图悬停** | 单格 `scale(1.35)` + 浮层淡入 | 120 ms / fast |
| **统计数字变化** | 数字滚动进位 | 120 ms |

### 5.6 无障碍与降级

- 全局遵守 `@media (prefers-reduced-motion: reduce)`：所有动效降为 ≤ 100 ms 的透明度变化
- 焦点环必须可见且高对比；全功能键盘可达
- 文本对比度 ≥ 4.5:1，大字号 ≥ 3:1
- 动效**永不作为唯一反馈**
- **热力图不能只靠颜色区分**：提供数值浮层与可选的纹理/亮度双通道，照顾色觉障碍用户

### 7.2 SVG 图标规范

### 7.4 应用图标：羽毛（占位资产）

**状态说明（v1.2）**：当前 `assets/icon.svg` 是**第一阶段使用的占位资产**。用户明确表示「画的不是很好，但可以暂时使用，第一阶段完成后自行重新设计」。因此本阶段的图标工作要求从「做出最终图标」降级为「**建立可替换的资产管线**」：

- `assets/icon.svg` 是**唯一源文件**，全平台资产由 `scripts/gen-icons.mjs` 派生
- **替换图标 = 换掉这一个 SVG 文件 + 重跑脚本**，不涉及任何代码改动
- 派生产物（`.ico` / `.icns` / PNG 集）**不入 git**，构建时生成

**现有草案的设计约束**（供后续重新设计时参考）：

| 项 | 规范 |
| --- | --- |
| 表现手法 | **线性（描边）风格**，非实心剪影 |
| 主图形 | 直立羽毛：闭合羽片轮廓 + 贯穿羽轴（下端延伸出羽根）+ 左右对称的 V 形羽枝 |
| 背景 | 圆角方形（`rx=224`），`135°` 线性渐变，深青墨 `#2B6B5F` → `#17423B` |
| 前景 | 近白 `#EAF4F0`，对比度 > 12:1 |
| 倾斜角 | 6° |
| 小尺寸 | ≤ 32 px 切换到 `icon-mark.svg`（去掉羽枝，只留轮廓 + 羽轴） |

**设计验证（实测记录，务必保留）**：羽毛图标有一个真实的陷阱——**流畅的杏仁形剪影会被读成叶子或水滴，而不是羽毛**。本次实际渲染并比对过 6 版：

| 版本 | 做法 | 实测结果 |
| --- | --- | --- |
| v1 / v2 | 实心羽片，无内部结构 | 被读作「叶子 / 水滴」，失败 |
| v3 | 实心羽片 + 从单点放射的羽枝线 | 更糟：放射线读成**叶脉**，强化叶片感 |
| v4 | 实心剪影 + 裸露羽根 | 仍是圆润水滴，失败 |
| v5 | 描边轮廓 + 贯穿羽轴 + 对称 V 形羽枝 | **成立**：羽枝与羽轴的夹角产生明确的羽毛语义 |
| v6（当前） | v5 基础上加密羽枝至 22 条、沿轮廓宽度渐变收束 | 300 / 128 px 下清晰可辨为羽毛 |

**结论**：羽毛必须由**「轮廓 + 中轴 + 对称羽枝」三者共同表达**，且**不能用实心填充**——实心会淹没羽枝，只剩一个类似叶片的色块。后续重新设计时应继承这条约束。

### 7.5 内置字体规范

#### 7.5.1 选定的字体

| 用途 | 字体 | 授权 | 说明 |
| --- | --- | --- | --- |
| 宋体族 | **思源宋体 SC**（Source Han Serif SC） | SIL OFL 1.1 | Adobe + Google 合作，与 Noto Serif CJK SC 同源同设计；衬线端正，适合长篇阅读 |
| 楷体族 | **霞鹜文楷**（LXGW WenKai） | SIL OFL 1.1 | 基于 FONTWORKS Klee One 派生，手写楷体气质 |

两者都是开源字体，可自由再分发，与 MIT 许可证兼容。**字体本身仍受 OFL 约束，不因项目是 MIT 而改变。**

#### 7.5.2 字体作用域与自由选择（v1.2 扩充）

用户明确要求「楷体也需要用到其他地方，用户有自由选择的权利」。因此字体**不是「正文宋体、标题楷体」的固定搭配**，而是一套**可自由指定的三个作用域**：

| 作用域 | 说明 | 可选项 |
| --- | --- | --- |
| 正文 | 编辑器正文排版 | 宋体族 / 楷体族 / 系统字体 |
| 标题 | 章节标题、卷名、书名的显示 | 宋体族 / 楷体族 / 系统字体 |
| 界面 | 应用 UI 文本（侧栏、菜单、按钮） | 宋体族 / 楷体族 / 系统默认 |

- 每个作用域**独立选择**，互不约束
- 每个作用域可继承「全局字体偏好」，也可单独覆盖
- 设置项同时支持**全局级**与**工作区级**（不同作品可用不同字体）
- 楷体因此**必须提供常规 + 粗体两个字重**（v1.1 曾考虑省掉楷体粗体以节省 2.5 MB，**此方案作废**）

#### 7.5.3 为什么必须子集化

2.4 节实测：全量中文字体单字重 17–24 MB。四个字重（宋常/宋粗/楷常/楷粗）全量内置会超过 60 MB，与要求②严重冲突。

**因此子集化是必选项**：

- **子集范围**：《通用规范汉字表》8105 字 + 常用标点 + 数字 + 拉丁字母 + 常用符号，约 9000–9500 字符
- **格式**：WOFF2（Brotli 压缩，比 TTF 小约 40%）
- **预估体积**：单字集约 2.5–3 MB，共 4 个字重约 **10–12 MB**

#### 7.5.4 缺字回退（重要）

子集化必然丢掉表外生僻字。小说作者在**人名、地名、功法名**上恰恰爱用生僻字，这是真实的产品风险：

- CSS `font-family` 提供完整回退链（见 5.2 节）
- 浏览器**按字符**回退：内置字体缺哪个字，就用回退链里下一个字体的那个字
- 结果：常见字用内置字体，生僻字自动落到系统字体，**不出现豆腐块**

缓解措施：

1. 回退链按「风格最接近」排序
2. 提供设置项「**完整字形模式**」：从 GitHub Release 下载完整字体包（约 50 MB），覆盖全部生僻字。**依赖 GitHub Releases，不需要自建服务器**，与 4.5 节约束一致。列为 Could，第二阶段实现

#### 7.5.5 内存影响与控制

| 手段 | 做法 |
| --- | --- |
| 按需加载 | `FontFace` API + `document.fonts.load()`，首次真正用到时才加载 |
| 只加载在用字族 | 三个作用域**共用**同一字族实例，不重复加载 |
| 粗体延迟 | 粗体字重仅在有粗体文本渲染时加载 |
| 上限保护 | 同时加载的字族数上限 2；超出时释放最久未用的（`document.fonts.delete()`） |
| 验收 | 指标 M5 / M6 |

#### 7.5.6 许可证合规（OFL 1.1）

子集化在 OFL 下构成 **Modified Version**：

| 要求 | 我们的做法 |
| --- | --- |
| 不得使用保留字体名（RFN） | **子集一律重命名**为 `Yuhua Serif SC` / `Yuhua Kai SC` |
| 必须随附版权声明与 OFL 全文 | 随包 `licenses/OFL-1.1.txt` + 原始版权行；应用内「关于 → 开源许可」可查看 |
| 不得单独售卖字体 | 字体不单独分发售卖 |
| 不得用原作者名义背书 | 致谢仅作事实性署名 |

**工程约束**：

- **字体二进制不入 git**。`scripts/fetch-fonts.mjs` 从官方 Release 下载固定版本并校验 SHA256，`scripts/subset-fonts.mjs` 完成子集化与重命名
- 版本号与哈希写入 `assets/fonts.lock.json`，保证任何机器、任何时间的构建产物一致
- CI 缓存下载结果

#### 7.5.7 体积降级阶梯

若 WOFF2 子集超 12 MB 预算，按顺序降级，**每级都要记录原因**：

1. 子集范围收缩到《通用规范汉字表》一级 + 二级（6500 字）—— 约省 25%
2. 改用可变字体子集（一个文件覆盖多个字重）—— 约省 30%
3. 楷体改为可选下载（仅内置宋体）—— 约省 5–6 MB（**会牺牲用户选择权，需用户确认**）

> 注意：v1.1 的「去掉楷体粗体」已因用户要求字体自由选择而**作废**。

## 9. 导出引擎设计（v1.2 新增，独立里程碑 M7）

### 9.1 支持格式与能力矩阵

| 格式 | 用途 | 段落/标题 | 粗斜体 | 列表 | 引用 | 分页 | 内嵌字体 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **TXT** | 交稿（最通用） | 标题转纯文本行 | 忽略 | 转 `-` 前缀 | 转 `>` 前缀 | 可选分页符 | 不适用 | 可设换行宽度、首行缩进 |
| **Markdown** | 归档 / 再编辑 | 完整保留 | 保留 | 保留 | 保留 | 卷章为标题层级 | 不适用 | 剥离 Front Matter，可选保留 |
| **HTML** | 网页预览 / 打印 | 完整保留 | 保留 | 保留 | 保留 | 章节分节 | 可选 Base64 内嵌 | 自带响应式排版 CSS |
| **DOCX** | 投稿 / 编辑 | 内置标题样式 | 保留 | 支持 | 支持 | 每章分页 | 仅声明字体名 | 符合 OOXML，Word/WPS 可开 |
| **PDF** | 打印 / 阅读稿 | 完整排版 | 保留 | 保留 | 保留 | 卷首分页 | **必须嵌入子集** | 见 9.4 技术风险 |
| **EPUB** | 电子书 / 多平台 | EPUB3 nav | 保留 | 支持 | 支持 | 每章一文件 | 可选内嵌 | 过 epubcheck 校验 |

**范围选择**：任意格式均支持「当前章 / 选中章节 / 整卷 / 整书」四种范围。

### 9.2 架构：单一 IR + 六渲染器

```
Markdown 文件（真源）
      │
      ▼  pulldown-cmark（CommonMark + GFM 子集）
   ┌──────────────────────────────┐
   │  yuhua-export :: Document IR │
   │  Book > Volume > Chapter     │
   │    > Block{ Paragraph,       │
   │      Heading, Quote, List,   │
   │      Code, Hr, PageBreak }   │
   │    > Inline{ Text, Emph,     │
   │      Strong, Code, Link }    │
   └──────────────┬───────────────┘
                  │
   ┌──────┬───────┼───────┬───────┬───────┐
   ▼      ▼       ▼       ▼       ▼       ▼
  TXT     MD    HTML    DOCX    PDF    EPUB
```

**关键设计决策**：

1. **导出在 Rust 侧完成**。理由：不整书进内存（不变量 5）、产物确定可测试、避免引入 pdfmake / docx.js 等重型 JS 依赖（违背要求②）。
2. **Markdown 解析用 `pulldown-cmark`**。风险是「编辑器用 JS 的 Lezer，导出用 Rust 的 pulldown-cmark，两套解析器可能漂移」。缓解：**明确冻结受支持的 Markdown 子集**（见 9.3），编辑器的功能面不超出该子集，并建立一致性测试。
3. **依赖最小化**：全部格式仅需 `pulldown-cmark` + `zip`（DOCX 与 EPUB 都是 zip 容器）。**不引入排版框架**。

### 9.3 支持的 Markdown 子集（冻结清单）

| 语法 | 支持 | 导出行为 |
| --- | --- | --- |
| `#` ~ `######` 标题 | 是 | 映射为各格式的标题层级 |
| 段落 | 是 | — |
| `**粗体`** / `*斜体*` / `***粗斜***` | 是 | 各格式原生映射 |
| `> 引用` | 是 | DOCX 用缩进+斜体样式；EPUB/HTML 用 blockquote |
| 无序 / 有序列表 | 是 | 原生映射；嵌套层级上限 3 |
| `---` 分割线 | 是 | 各格式分隔符 |
| 行内 `代码` | 是 | 等宽字体，不保证中文字体覆盖 |
| 代码块 | 是 | 等宽块，不做语法高亮 |
| 链接 / 图片 | 是（链接） | 图片在 DOCX/EPUB 中**内嵌**；PDF 内嵌；TXT 丢弃 |
| 表格 | **否**（第一阶段） | 降级为纯文本缩进，并在导出报告中提示 |
| 脚注 | **否** | 降级为括号内联 |
| LaTeX 公式 | **否** | 原样保留文本 |
| 原始 HTML | **否** | 转义为文本 |

> 表格与脚注的缺席要在**导出前给用户明确提示**，不能静默丢内容。

### 9.4 各格式实现要点

**TXT**
- 逐章流式写出，可选「每章之间插入分页符 `\f`」
- 可配置：换行宽度（默认 0 = 不硬换行）、首行缩进（默认 2 个全角空格）、章节标题格式

**Markdown**
- 直接拼接原文，剥离 Front Matter（可选保留）
- 卷作为 `#`，章作为 `##`（可配置层级偏移）

**HTML**
- `pulldown-cmark` → 正文 HTML + 内置模板 + 排版 CSS
- 可选 **Base64 内嵌字体子集**，使单文件 HTML 离线保真（体积换便携）

**DOCX（OOXML，手写最小实现）**
- 结构：`[Content_Types].xml` + `_rels/.rels` + `word/document.xml` + `word/styles.xml` + `word/fontTable.xml`
- 用 `zip` crate 打包，**不引入 docx 生成库**
- 样式：`Heading1/2/3`、`Normal`、`Quote`、`ListParagraph`，在 `styles.xml` 中显式声明中文字体（宋体/楷体随用户设置）
- 每章 `<w:br w:type="page"/>` 分页
- **不做**：复杂表格、文本框、图片环绕、目录域

**PDF（技术风险最高，需 Spike）**
- **首选方案**：复用系统 WebView 的「打印到 PDF」能力，从生成的打印就绪 HTML 出 PDF
  - 优点：零额外依赖；与所见即所得一致；字体随渲染器嵌入，中文可搜索
  - 实现：Windows 走 WebView2 的 `PrintToPdf`；macOS 走 WKWebView 的 PDF 导出；Linux 走 WebKitGTK 打印
  - **风险**：三平台 API 差异大，Tauri 2 未必直接暴露，可能需要平台特定绑定代码
- **备用方案**（若首选方案在某平台不可行）：引入纯 Rust PDF 渲染（`printpdf` 或 Typst 库），代价是二进制体积增加与二进制体积/编译时间上升
- **T7.x 中安排 Spike 任务**：先在 Windows 打通首选方案，评估另两平台可行性，产出结论文档

**EPUB（EPUB 3）**
- 结构：`mimetype`（必须**无压缩且第一个**写入）+ `META-INF/container.xml` + `OEBPS/content.opf` + `nav.xhtml` + 每章一个 XHTML
- 元数据：标题、语言、作者（可在导出面板填写）、UUID、修改时间
- **CI 中用 `epubcheck` 校验**，必须零 error
- 可选内嵌字体子集（评估各阅读器兼容性后再定是否默认开启）

### 9.5 导出交互

- **入口**：`Ctrl/Cmd + E` 或章节右键菜单「导出」
- **面板**：格式选择（六选一）→ 范围选择 → 格式专属选项 → 目标路径
- **选项记忆**：每个格式独立记住上次配置（Should 项）
- **进度**：Rust 侧通过事件推送进度（已处理 N/M 章），前端用**自绘 SVG 进度环**展示，完成时对勾描边动画
- **可取消**：任意时刻取消，清理未完成的临时文件
- **导出报告**：完成或结束后展示一份简报 —— 成功章数、跳过章数、**降级提示**（如「3 章包含表格，已降级为纯文本」）
- **原子产出**：先写临时文件，成功后才重命名到目标路径，避免半截文件

### 9.6 明确不做的

- 多格式批量并排导出（一次选多种格式）
- 自定义导出模板编辑器（第一阶段用内置模板 + 少量参数）
- PDF 的书签目录、页眉页脚、页码样式深度定制
- DOCX 的目录域、交叉引用、批注

## 10. 写作统计与数据记录（v1.2 新增，独立里程碑 M8）

### 10.1 功能清单

| 功能 | 说明 |
| --- | --- |
| **码字日历** | 月视图日历，每天格子显示当日码字量，颜色深浅表示强度；点击某天查看当天明细 |
| **年热力图** | GitHub 贡献图风格，53 周 × 7 天；悬停显示日期与字数 |
| **写作记录** | 每次写作会话：开始时间、持续时长、码字量、涉及章节 |
| **连续天数** | 连续码字天数（当日字数 ≥ 阈值才计入，阈值可设，默认 100 字） |
| **日/周目标** | 设定目标字数，显示完成进度环与达成状态 |
| **汇总统计** | 总字数、本月、本周、今日、平均日更、最高单日、累计写作时长、预计完稿日 |
| **分章统计** | 各章字数排行、卷分布 |

### 10.2 数据来源：如何计算「今天写了多少字」

三种可选口径，**默认采用最可靠的一种**：

| 口径 | 做法 | 评价 |
| --- | --- | --- |
| **章节字数差分（默认）** | 保存时对比该章的上次字数与当前字数，正差计入当日 | 简单、可靠；**只增不减地记录增长**，删改导致的负差不抵扣 |
| 会话内计数 | 累计本次会话的输入字符数 | 不受删改影响，但重启或崩溃会丢 |
| 编辑器增量 | 监听每次编辑操作 | 最精确，但开销大，违背要求② |

**决定：以「章节字数差分」为主，会话计数为辅**。两者都记录，日历与热力图用差分数据（稳定），写作记录用会话数据（能体现时长）。

**只记增长**的理由：作者大量修改旧章是常态，若让删减抵扣当日产量，会出现「今天写了 3000 字却显示 -2000」的荒谬结果。

### 10.3 存储结构（纯文本，云盘安全）

`.yuhua/stats/daily-YYYY-MM.json`：

```json
{
  "schema": 1,
  "days": {
    "2026-01-15": {
      "chapters": { "ch_01J8XK2M9P": 1520, "ch_01J8XK3Q4R": 980 },
      "sessions": [
        { "start": "2026-01-15T09:12:00+08:00", "minutes": 47, "words": 1520 }
      ],
      "goal": 3000
    }
  }
}
```

**设计要点**：

- 按**月**分文件，单文件小、写入局部、冲突面窄
- **只存增量（当日新增字数）**，不存累计值 —— 累计值可由章节字数实时算出，存了反而容易不一致
- `chapters` 以章节 ID 为键，为下面的冲突合并提供基础

### 10.4 多设备合并规则（与 4.5 节云盘同步配套）

统计文件会随工作区被云盘同步，可能产生冲突副本。合并规则设计为**单调、可交换、可重复（CRDT 式）**，因此**任意合并顺序结果一致，且不会重复计数**：

| 数据 | 合并规则 | 理由 |
| --- | --- | --- |
| `days[d].chapters[c]` | **取最大值** | 同一章同一天的增量是单调的；取 max 可防止把两台设备的产出相加导致翻倍 |
| `days[d].sessions` | **按 `start` 时间戳去重后并集** | 会话天然带唯一时间戳 |
| `days[d].goal` | 取最后修改者（时间戳新者胜） | 目标是用户显式设置，不是累加量 |
| 跨月文件 | 按文件名分片，互不影响 | 减少冲突面 |

**说明与局限**（要写进用户文档）：若在两台设备上**同一天分别写了不同章节**，合并后两块增量都会保留（因为键不同），这是正确的；但若两台设备**改的是同一章**，取 max 会取较大的一次，可能少算 —— 这是为避免翻倍计数的自觉取舍，误差有界。

### 10.5 渲染方案：纯 SVG 自绘（要求 ②③）

**不引入任何图表库**。三种视图都用 SVG 生成：

| 视图 | 实现 |
| --- | --- |
| 月历 | 7 列 × 6 行网格，每格一个 `<rect rx=3>`，填充色按当日字数映射到色阶；当天加描边 |
| 年热力图 | **单个 `<svg>` 内 365 个 `<rect>`**，一次插入 DOM；不用 365 个组件节点 |
| 进度环 | 两个 `<circle>` + `stroke-dasharray` 控制弧度 |
| 数字 | 等宽数字（`font-variant-numeric: tabular-nums`）防跳动 |

**性能约束**：

- 热力图渲染一次完成，**逐格不做动画**（365 个同时动画直接违反要求②）
- 色阶映射用预计算的 5 档颜色数组，不做逐格 JS 计算
- 悬停交互用事件委托（一个监听器），不绑定 365 个监听器

### 10.6 隐私说明

统计只记录**字数与时间**，**不记录任何正文内容**，不联网上报。数据完全在用户自己的工作区内，用户可随时删除或查看。这一点写进用户文档。

### 13.1 产品验收（逐条可演示）

## 15. 开源工程化

| 项 | 方案 |
| --- | --- |

| 文档 | `docs/` 存设计文档；README 面向用户，CONTRIBUTING 面向贡献者 |

### 仍待确认（不阻塞 M0–M2，但影响 M7/M8）

1. **PDF 导出若首选方案在 macOS/Linux 不可行，是否接受引入纯 Rust 渲染带来的二进制体积增加？** 这会与安装包预算冲突，需要你权衡。Spike 完成后我会带着实测数据来问。
2. **EPUB 是否默认内嵌字体？** 内嵌能保证阅读器里排版一致，但会显著增大 EPUB 体积，且部分阅读器忽略内嵌字体。默认建议：第一阶段**不内嵌**，作为导出选项提供。
3. **DOCX 是否需要在章与章之间保留卷标题页？** 影响投稿格式。默认建议：卷作为 Heading1，章作为 Heading2，不单独分页。
4. **导出时的作者名、书籍简介等元数据由哪里填？** 建议在导出面板里填并记住；也可后续加进工作区配置。
5. **统计的连续天数阈值默认多少？** 当前建议 100 字。太低会让「连续」失去意义，太高会打击积极性。
6. **是否需要「预计完稿日」这类推算？** 当前包含在汇总统计里，算法为「剩余字数 ÷ 近 7 日平均日更」。若认为不够准可以去掉。
7. **是否需要把统计页做成可导出/可分享的图片？** 当前不做。会与「零外链、纯 SVG」不冲突，但增加工作量。

## 附录 B：完成定义（Definition of Done）

一个任务算完成，当且仅当：

1. 代码已合并到 `main`
2. 相关单元 / 集成测试通过，新增逻辑有测试覆盖
3. `cargo clippy -D warnings` 与前端 lint 全绿
4. 涉及 UI 的改动，动效符合 5.5 节清单且实测 60fps
5. 涉及性能敏感路径的改动，基准未退化
6. 涉及字体或资源的改动，已核对 OFL 合规与体积预算
7. **涉及导出的改动，已在真实办公软件 / 阅读器上打开验证过产物**
8. 文档（设计文档、CHANGELOG）已同步更新

## 附录 C：羽毛图标设计规范

**几何构造**（1024 × 1024 主稿，线性描边风格）：

| 元素 | 参数 |
| --- | --- |
| 底板 | 圆角方形，`rect(0,0,1024,1024, rx=224)` |
| 底板填充 | 线性渐变 135°，深青墨 `#2B6B5F` → `#17423B` |
| 整体变换 | `rotate(6, 512, 512)` |
| 羽片轮廓 | 闭合路径，`stroke-width: 22`，圆头圆角，**无填充** |
| 轮廓控制点 | `M512 142` → `C614 262 656 414 638 522` → `C622 616 570 682 512 706` → `C454 682 402 616 386 522` → `C368 414 410 262 512 142 Z` |
| 羽轴 | `M512 142 C514 400 512 640 506 896`，`stroke-width: 20`；下端延伸出羽片形成裸露羽根 |
| 羽枝 | 22 条 V 形短划，自羽轴左右对称伸出，端点落在轮廓内侧约 86% 宽度处；`stroke-width: 13`，`opacity: 0.92` |
| 羽枝分布 | `y` 从 216 到 600，步长 38；**半宽沿抛物线渐变**（峰值在 `y=480`） |
| 前景色 | 近白 `#EAF4F0`，对比度 > 12:1 |
| 倾斜角 | 6° |

**关键约束**：羽枝必须与羽轴成**锐角且左右对称**。若改成从单点放射（如 v3 的做法），视觉上会变成叶脉，反而强化叶片联想——这是实测踩过的坑。

**资产清单**：

- `assets/icon.svg` — 1024 主稿（**唯一源文件**，替换即整体换肤）
- `assets/icon-mark.svg` — 24 px 线性标记（应用内品牌位）
- `scripts/gen-icons.mjs` — 派生 `.ico` / `.icns` / PNG 集
