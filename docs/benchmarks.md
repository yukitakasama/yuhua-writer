## 如何采集

```bash
pnpm bench          # 环境信息、前端产物体积、待运行测试数
```

自动采集写出 `docs/benchmarks-generated.md`。内存类指标里，**冷启动应用组**
（M1 / M1b / M4）需要启动真实窗口，**导出类**（M7 / P8 / P9 / P10 / P5）
可以无头采集。三件采集工具与用法：

```bash
# 一次性产物（release exe + 导出夹具）
pnpm exec tauri build --no-bundle
cargo build --release -p yuhua-export --example export_peak
```

```powershell
# M1 / M1b / M4：启动真实窗口，轮询整棵进程树（1 个主进程 + 6 个 WebView2 子进程）
# 空闲 CPU 用窗口内增量，并按进程分解（M4_PER_PROCESS）
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/bench/measure-coldstart.ps1 `
  -Exe "D:\path\to\target\release\yuhua-writer.exe" -SettleSec 180 -SampleSec 300 -IntervalMs 5000

# M7 / P8 / P9 / P10：外部按 10–20 ms 轮询被测进程的 WorkingSet
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/bench/measure-peak.ps1 `
  -Exe "D:\path\to\target\release\examples\export_peak.exe" -AppArgs m7 -IntervalMs 20

# P3 代理：进程启动到主窗口句柄出现，4 次取中位
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/bench/measure-startup.ps1 `
  -Exe "D:\path\to\target\release\yuhua-writer.exe" -Runs 4

# P4 / P3 应用内段：埋点在应用里，读数在界面上（真机跑一次，打开一章再看）
pnpm tauri dev            # 打开书 → 点一章 → 设置 → 关于 → 运行诊断
```

```bash
# P5：百万字检索（真测试，进 CI，不需要上面任何工具）
cargo test -p yuhua-store --release --test search_scale -- --nocapture

# P10 反证：用外部工具从导出的 PDF 里提取中文（不是自证结构合法）
pdftotext -enc UTF-8 <导出的.pdf> out.txt
```

三个 `measure-*.ps1` 用 PowerShell 而不是 bash：Windows 的进程工作集与
CPU 时间只能从 `Get-Process` / `Get-CimInstance` 拿，`ps` 不报这些。
它们都会强制关掉**自己启动的**那个进程树，不碰其它实例。

调这三个脚本时会遇到的两个坑，都已经踩过：

- **`-File` 前要用 `powershell.exe` 的绝对路径**（或在交互式终端里用
  `pwsh`）。在自动化 / 非登录的 shell 环境里 `pwsh` 这个命令经常解析不到，
  表现是退出码 127 且**什么都不输出** —— 看着像脚本崩了，其实命令没跑成。
- **三个 `.ps1` 必须是带 BOM 的 UTF-8。** 文件里有中文注释，而 Windows
  PowerShell 5.1 读无 BOM 的文件时按系统 ANSI 代码页（本机 GBK）解码，
  多字节序列会吃掉相邻字符、把脚本结构改坏，报出来的是「无法对 Null 数组
  进行索引」这类看不出根因的错。`pwsh` 7 默认按 UTF-8 读，所以只在 5.1 上
  复现 —— 别用「本地能跑」来判断这几个文件是好的。

## 各指标的实测细节

### M1 / M1b / M4：冷启动应用组

方法：启动 `target/release/yuhua-writer.exe`，等 180 秒让启动期工作完全落地，
之后按真实流逝时间采样**整棵进程树**（1 个 `yuhua-writer` + 6 个
`msedgewebview2`）的工作集与私有内存，连续 300 秒；CPU 用**窗口内的增量**
而不是进程累计值。

两次独立采集（首测 10-06，间隔 45 秒轮询 298 秒；复测 10-07，间隔 5 秒轮询
295.5 秒，跑在修掉偏差 2 那个缺陷之后）：

| 采样项                             | 首测 10-06             | 复测 10-07             |
| ---------------------------------- | ---------------------- | ---------------------- |
| 主进程工作集（尾 60s 均值 / 峰值） | 45.22 / 45.23 MB       | 44.93 / 44.97 MB       |
| 进程树工作集之和（均值 / 峰值）    | 471.53 / 476.88 MB     | 456.72 / 457.83 MB     |
| 进程树私有内存之和（均值 / 峰值）  | 207.61 / 214.83 MB     | 202.75 / 203.29 MB     |
| 空闲 CPU 增量（占单个逻辑核）      | 44.11%（见偏差 2）     | **0.100%**             |
| 全程趋势                           | 206→208 MB，无单调增长 | 202→203 MB，无单调增长 |

两个口径的区别必须写清楚：**工作集之和会把共享页重复计数**（WebView2
六个进程共享大量 DLL 与共享内存段），所以它显著高估真实占用；
任务管理器「应用」分组显示的是私有工作集，对应这里的**私有内存之和**。

复测这一轮还有一个副产品：树总量 0.100% 是树里**每一个**进程的上界，
所以「空闲时到底是哪个 WebView2 子进程在占 CPU」这个问题已经不需要
单独归因了 —— 修复前它占 37.40%，现在任何单个进程都不可能超过 0.100%。
拿 471 MB 去比 150 MB 的预算是错的读法。

### M7 / P8 / P9：导出规模实测

夹具：`src-tauri/crates/yuhua-export/examples/export_peak.rs`。
正文经 `ChapterSource` **按需生成**（不把全书 Markdown 塞进领域模型），
每种格式重复 20 次取中位数，内存由外部按 20 ms 轮询 WorkingSet。

| 规模              | 装配  | TXT  | DOCX  | EPUB  | HTML  | PDF               |
| ----------------- | ----- | ---- | ----- | ----- | ----- | ----------------- |
| 325,100 字/100 章 | 5 ms  | 3 ms | 8 ms  | 14 ms | 6 ms  | 102 ms / 14.05 MB |
| 975,300 字/300 章 | 16 ms | 7 ms | 18 ms | 22 ms | 13 ms | 257 ms / 17.77 MB |

峰值内存：30 万字 9.50 MB、100 万字 19.81 MB（都不含 PDF）；
同轮把 PDF 也算进去时，30 万字 49.04 MB、100 万字 67.79 MB（私有 80.71 MB）。

**结论与两点限定**：

1. 预算里 M7 是「100 万字 / 300 章 ≤ 120 MB」，实测最坏口径 67.79 MB（含 PDF）
   —— 达标，余量约 1.8 倍；不含 PDF 时余量约 6 倍。
2. **PDF 是内存与耗时的大头**，不是 DOCX / EPUB。原因是渲染器按接口约定
   返回「已完成产物的字节」，而一份 100 万字的 PDF 本身就是 17.8 MB
   （其中内嵌字体占相当比例），再加上排版中间结果。
3. **合成语料高度重复，所以体积与耗时都偏乐观**：DOCX 的 `document.xml`
   实际是 3,230,552 字节，被压成 26,406 字节（136:1）——真实稿子不会这么可压。
   耗时一侧同理（重复文本对缓存友好）。这两条只够证明「导出不是瓶颈」，
   不能当成「真实交稿的耗时」。

### P5：100 万字检索

测试：`src-tauri/crates/yuhua-store/tests/search_scale.rs`（release 跑）。

- `search_on_million_chars_meets_p5_budget` —— 100 章 × 1 万字（975,300 字）
  建索引（166 ms），5 个真实存在于正文的关键词各查 5 次取中位数，
  断言最慢的一条 < 300 ms
- `million_char_corpus_actually_has_the_expected_volume` —— 用召回数反证
  语料规模没退化（每个关键词命中 100 条 = 章数）

实测中位数区间 **184–303 µs**，即预算的约 0.1%。
关键词刻意选「语料里真实存在的词组」：查不到的词会提前返回，
测出来的是空结果的成本，不是「在一百万字里合并 posting」的成本。

### P3：冷启动（代理指标）

方法：`Start-Process` 到主窗口句柄非零，4 次取中位 = **285 ms**
（236 / 284 / 285 / 428 ms）。

**这不是「可输入」**：句柄出现只说明窗口建好了，页面加载、SolidJS 启动、
CodeMirror 挂载都还没被覆盖。真实的编辑器就绪必须在应用内埋点。

**2026-10-07：应用内埋点已接线**（`src/app/perf.ts`）。`markEditorReady()`
在 CodeMirror 视图建好的那一刻记下「模块求值 → 编辑器就绪」的毫秒数，读数入口是
设置 → 关于 → 运行诊断。要注意**时钟边界**：`performance.now()` 的原点是
文档开始加载，不是进程启动，所以这个数**不能**与上面的 336 ms 相加 ——
两个时钟没有共同原点，相加得到的「冷启动总时间」是假的。报告时分两段写：
进程启动 → 窗口出现（外部探针）、模块求值 → 编辑器就绪（应用内）。
口径上还有一条要写清楚：这里记的是**视图建好**，不是「能打字」——
编辑器现在一直挂着，正文还在读时它已经存在但处于只读，把只读期算进去
就会和 P4 混成一团，两个数各自在测什么就说不清了。
数值要真机跑一次才有；jsdom 里跑出来的数没有任何意义。

2026-10-07 02:39 在**打包后的** exe 上重跑了一次同法探针：
320 / 333 / 347 / 792 ms，中位 **336 ms**（首轮 792 ms 是磁盘缓存冷）。
与打之前的 285 ms 同一量级，说明打包与资源内嵌没有给启动加台阶。

### P4：打开 1 万字章节（应用内埋点已接线，数值待真机采集）

这一项的两端**都在应用内**（发起读章请求 → 正文灌进 CodeMirror 视图），
同一个 `performance.now()` 时钟，所以它不像 P3 那样需要代理指标。

| 埋点 | 位置                                           | 说明                          |
| ---- | ---------------------------------------------- | ----------------------------- |
| 起点 | `workspace-store.ts` 的 `loadChapterBody` 入口 | IPC 请求发出之前              |
| 终点 | `EditorPane.tsx` 的灌正文 effect               | 正文已在编辑器视图里          |
| 读数 | 设置 → 关于 → 运行诊断                         | 最近一次 / 最近 20 次的中位数 |

终点刻意放在「灌入视图」而不是「IPC 返回」：返回处只覆盖后端读盘，
渲染那半才是作者感到的卡。中位数而不是均值 —— 一次 GC 就能把均值拉歪。

**口径补充（2026-10-07）**：换章原先会**卸载再重建**整个 CodeMirror 视图，
所以那段时间里混着「构造编辑器」的成本；现在编辑器一直挂着，换章走
`resetDocument`（重建状态、撤销历史归零），只读由 Compartment 表达。
因此 P4 量的自此是「读盘 + 把正文装进视图」，不再包含视图重建 ——
这与作者的体感更一致：重挂视图带来的滚动位置与焦点丢失本来就不该算「快」。

**接线过程本身抓到一个大 bug**：读章只在 `EditorPane` 的 `onMount` 里发起，
而该组件不随换章重建，于是「工作区开着再点某一章」根本不会去读文件，
编辑器停在上一章的内容上（冒烟测试里 `perf` 一条样本都没产生才暴露的）。
后续排查又带出五条同类缺陷，详见 CHANGELOG「装配层接线审查轮」。

而它恰恰是当初假设会撑爆预算的那一项。这条记录留着，是为了说明
**未测的悲观预测不该被写成结论**。

# 只有一个 payload：yuhua-writer.exe（前端与字体由 Tauri 内嵌进 exe）+ uninstall.exe

且 `webviewInstallMode = downloadBootstrapper` 意味着**安装时需要联网**拉 WebView2 运行时。

### P10：PDF 中文可搜索可复制

用**外部工具反证**而不是自证结构合法：

## 偏差记录

### 偏差 1：M1 / M1b 未达标（冷启动内存超预算）

- 实测：主进程 45.22 MB（预算 30 MB）；应用组私有内存 207.61 MB（预算 150 MB）。
- 拆分：**WebView2 六个子进程占约 162 MB 私有内存**，即应用组的八成；
  Rust 主进程 45 MB。也就是说这不是「我们的代码吃掉了 200 MB」，
  而是**系统 WebView 本身的基线**。
- 根因（三层，按可控程度排序）：
  1. `≤ 150 MB` 这个预算是计划书阶段定的，当时没有实测依据；WebView2 在
     Windows 上跑任何一个空页面都要起 browser / GPU / renderer / utility /
     network / crashpad 六类进程，基线就在 150–200 MB 量级。
  2. 主进程 45 MB 高于 30 MB 预算。这一度被归因于「release 构建仍带
     `debuginfo`」——**这个假设已推翻**（见下方「假设的更正」）。
  3. 没有对 WebView2 做任何参数裁剪（`AdditionalBrowserArguments`），
     也没有关掉 crashpad 等可选组件。
- 后续计划（优先级顺序，均需人拍板后才动）：
  1. **先定口径**：把 M1 的定义改成「私有工作集」并给出 Windows 与
     Linux/macOS 分别的预算，或者显式承认 WebView 基线并把预算拆成
     「内核 ≤ 40 MB + 视图层 ≤ 200 MB」。现在的 150 MB 在 Windows 上
     是**不可能达标**的，留着只会在每次验收时重复报红。
  2. 试 `AdditionalBrowserArguments`（如 `--in-process-gpu`、
     `--disable-features=...`）与 `--renderer-process-limit`，看能省多少；
     这是唯一能真正减少 WebView2 进程数的杠杆，代价是隔离性下降。
  3. 主进程那 15 MB 超额怎么来的，目前**归因不了**，需要先做对照量法（见下）。

#### 假设的更正：原方案 → 新方案 → 原因

**原方案**：怀疑主进程 45 MB 里有一部分是「release 构建带了调试信息」，
计划把 `debug` 级别降到 `1` 或 `0`，再量一次主进程 RSS 来验证。

**新方案**：这个实验取消。改用**对照量法**归因 —— 同一份构建分别量
「空白窗口」与「实际书架页」两次主进程 RSS：差值才是前端与索引库那部分，
基线则是 Tauri + WebView2 宿主自身的固定开销。量出来之后再决定值不值得动。

**原因（两条各自独立成立，任一条都足以否掉原假设）**：

1. 配置里没有这条路。`Cargo.toml:95-100` 的 `[profile.release]` 是
   `opt-level = "z"` / `lto = true` / `codegen-units = 1` / `panic = "abort"` /
   `strip = true`，**根本没有 `debug` 键**，而 Rust 为 release 档填的默认值
   就是 `debug = 0`（不生成调试信息）；`strip = true` 又已经把符号从产物里
   去了。磁盘上的 exe 是 15,296,000 B，没有可再削的段落。
2. 机制本来就不对。调试信息是**可执行文件里不会被加载进常驻内存的段落**，
   它影响磁盘体积与崩溃符号化，不影响进程 RSS。即便它真的存在，
   降级别也量不出 RSS 变化 —— 这个实验即使「做出了变化」也不说明任何事。

所以 M1 / M1b 剩下的不是工程问题，而是**口径问题**：要么按上面第 1 条
后续计划把预算拆开，要么承认 Windows + 系统 WebView2 的基线就是这个量级。
在口径定下来之前，继续找「再省 10 MB」的技巧只是在给一个不可能的目标做工。

### 偏差 2：空闲 CPU 一度被一个装饰动画顶到单核 44%（已修复）

**现象。** 修之前，应用停在空界面上什么都不做，整棵进程树仍然稳定消耗
约 **44% 的单个逻辑核**（按 24 核算折合全机 1.8%）。计划书 6.2 的 M4 目标
是「空闲 5 分钟 CPU ≤ 1%」，这个值超标四十多倍，而且会在笔记本上持续耗电、
让风扇转起来 —— 对一个「写作工具」来说属于会被用户直接感知的缺陷。

**判定口径。** 这里采用**单核等价**（CPU 时间增量 ÷ 窗口秒数），不是全机占比。
理由：一个持续的后台空转无论落在几个核上，代价都是一个核的时间片与相应的
功耗；用全机占比当口径会让任何多核机器上的空转都自动「达标」。

**排查过程（每一步都推翻了前一个假设）。**

1. 先怀疑是采集器自身：整树数字里含每轮 `Get-CimInstance` 的开销。
   于是按进程分解，结果是主进程 `yuhua-writer` **0.00 s**、
   `renderer` 0.50 s、WebView2 的 **GPU 进程 9.64 s**（≈ 单核 24%）。
   开销假设不成立，问题在前端页面的合成侧。
2. 再怀疑 WebView2 的进程结构，试了 5 组启动参数（同一台机器、同一 exe）：

   | 启动参数                                         | 空闲 CPU（单核） |
   | ------------------------------------------------ | ---------------- |
   | 基线（不带任何参数）                             | 23.09%           |
   | `--in-process-gpu`                               | 49.62%           |
   | `--disable-gpu-compositing`                      | 44.58%           |
   | `--disable-features=CalculateNativeWinOcclusion` | 11.81%           |
   | `--disable-gpu`                                  | 45.35%           |

   没有一个能把它压到 1% 以下，说明不是进程裁剪问题。

3. 又怀疑是启动期的预热尾巴。把静置时间从 45 秒拉到 180 秒再测 90 秒，
   仍然 44.11%（GPU 进程 37.40%）—— **空转是常态，不是尾巴**。
4. 定位到 CSS：`src/styles/app.css` 里空状态的 `.empty__art` 带
   `animation: breathe 9s … infinite`，关键帧改的是 `transform: scale()`。
   无限循环的 `scale` 会强制那张 148px 的内联 SVG **每帧重新栅格化**，
   合成器因此永远闲不下来。
   它在书架页「没有最近工作区」时才渲染 —— 这也解释了为什么在浏览器里用
   mock 数据跑 `document.getAnimations()` 数到 0 个动画：那条路径根本没挂
   这个空状态。

**修复。** 呼吸改成只在「刚看到这个空状态」时播 3 轮、且只改 `opacity`
（不触发重新栅格化）：`animation: breathe 9s var(--e-standard) 3`，
关键帧里的 `scale` 删除。

**复测。** 同一台机器、同一口径（静置 180 秒 / 采样 300 秒）：
整树 CPU 增量 **0.30 s / 295.5 s = 单核 0.100%**，全机 0.004%。达标。

**防回归。** 新增 `src/design/motion/no-perpetual-animation.test.ts`（5 条断言），
扫全部样式源文件，规则是：无限循环的动画名必须在白名单里，白名单的判据是
「这个元素会不会在用户闲置时仍挂在页面上」；并且无限循环的关键帧不许改几何
属性（`scale` 等），除非有写明理由的豁免（`save-pulse` 是一颗只在保存期间存在的
6px 圆点）。把这次修的那两处单独钉住：`.empty__art` 不许 `infinite`、
`breathe` 不许有 `scale`。改回 `infinite` + `scale` 时这 2 条会红。

**顺带修掉的两个测量错误**（都属于「数字看着对其实不可信」）：

- `measure-coldstart.ps1` 的窗口长度是把每轮的 `-IntervalMs` **标称值累加**
  出来的，而每轮采样自身要花 1～几秒（枚举全机进程树找父进程）。分母被压短，
  同样的 CPU 增量算出几倍的百分比 —— 首测记录的「单核 7.51% / 22.38 s」
  就是这么来的，真实值是 44.11%。现在改用 `Stopwatch` 的真实流逝时间。
- 三个 `measure-*.ps1` 之前是**无 BOM 的 UTF-8**，Windows PowerShell 5.1 按
  GBK 解码中文注释时会破坏脚本结构，报出与根因无关的错。已补 BOM，
  并把这条写进脚本头部注释与「如何采集」。
