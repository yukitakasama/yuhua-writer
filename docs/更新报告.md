## 四、关键设计决策

这一轮做出的、会影响后续所有工作的决策：

### 1. 领域层不依赖 Tauri

`yuhua-core` / `yuhua-fs` / `yuhua-store` / `yuhua-export` / `yuhua-stats`
是**纯 Rust 库**，不引入任何 Tauri 依赖。好处：

- 测试跑在毫秒级，不需要启动窗口
- 未来的 CLI 工具、批量导入脚本、迁移工具可以直接复用
- 「命令层是薄壳」这条架构约束变成**编译期保证**而非口头约定

### 2. 索引库必须放在工作区之外

已用测试钉死（`workspace_contains_no_binary_db`）。原因是 SQLite 带
WAL 与共享内存文件，云盘对正在写入的二进制做部分同步极易损坏；
而索引本来就是可抛弃的缓存。这条约束是「工作区可安全放进云盘」的前提。

### 3. 索引库用纯 Rust 实现中文分词（零 unsafe）

FTS5 自带的 `unicode61` 把中文整句当一个词，`trigram` 要求查询串至少
3 个字符 —— 两者对两字中文词（「羽化」「写作」「主角」，中文里最常见的形式）
都不可用。

方案是**写前预分词**：写入前用二元组切分并用空格连接，
再交给 `unicode61`（按空格切分）。效果与注册自定义分词器等价，
但分词逻辑成为**可完整测试的纯函数**，且全程零 unsafe ——
与工作区 `unsafe_code = "forbid"` 的约定一致。

### 4. 所有「危险操作」都有测试钉死边界

| 保证 | 对应测试 |
| --- | --- |
| 原子写不留半截文件 | `overwrites_existing_file_completely` |
| 临时文件与目标同目录（否则 rename 不原子） | `temp_file_is_in_same_directory` |
| 索引库不在工作区内 | `workspace_contains_no_binary_db` |
| 冲突副本只提示不删除 | `detect_never_modifies_files` |
| 恢复回收站不覆盖现有文件 | `restore_refuses_to_overwrite_existing_file` |
| 路径不能逃逸出工作区 | `resolve_rejects_parent_escape` |
| 统计合并幂等、不重复计数 | 合并算法的乱序 / 重复 / 冲突副本测试 |

### 5. 前端零 emoji、零外链、零图标字体

已用脚本**独立扫描核验**：全仓无 emoji 字符（唯一命中是 Rust 测试用例里
的 `★☆`，那是验证「原子写能处理任意 Unicode」的测试数据，不是界面装饰），
无外链资源，无图标字体。55 枚图标全部手写 SVG，55 个独立文件便于 tree-shaking。

## 五、过程中发现并修复的真实缺陷

这些不是「跑通了」，而是**测试或验证过程中发现产品代码本身有问题**：

| # | 缺陷 | 影响 | 发现方式 |
| --- | --- | --- | --- |
| 1 | 搜两字中文词必然落空 | **检索功能对中文等同于不可用** | 排查集成测试失败 |
| 2 | `Index::rebuild` 不重建卷 | 重建索引触发外键失败 | 单元测试 |
| 3 | 动效并发配额泄漏 | 30 次动效后所有动效永久静默降级 | 单元测试 |
| 4 | 过阻尼弹簧时长严重低估 | 动画中途被截断 | 单元测试 |
| 5 | 临界阻尼包络少算多项式因子 | 动画差 0.8% 被截断 | 单元测试 |
| 6 | Dialog 焦点陷阱静默失效 | **键盘用户 Tab 能跑出弹层** | 组件测试 |
| 7 | Menu 方向键完全无法移动 | 菜单键盘操作不可用 | 组件测试 |
| 8 | `div[tabindex=0]` 永远不可聚焦 | 无原生控件的弹层焦点陷阱失效 | 组件测试 |
| 9 | Select 选中项永远停在第一项 | 下拉选择不可用 | 组件测试 |
| 10 | 云盘同步改 mtime 触发全量重索引 | 性能退化 | 设计时用双闸门规避 |

第 1 条尤其值得记录：**分词器为提升召回在每个 CJK 游程末尾补了一个
单字 token，查询侧却把它当成必要条件**，于是搜「羽化」要求索引里存在
独立的「化」—— 而正文切出的是 `羽化/化写/写作/作`，根本没有「化」。

修复后补了一条**契约测试**：查询串产生的每个 token 都必须在
「正文分词结果的 token 集合」中存在。这条测试能防止同类问题再次出现。

## 六、与计划书的偏离

所有偏离都写进了代码注释与 done-list，此处汇总：

| 项 | 计划书 | 实际 | 原因 |
| --- | --- | --- | --- |
| FTS5 分词器 | 注册自定义 tokenizer | 写前预分词 + `unicode61` | 自定义 tokenizer 需 unsafe FFI；预分词方案效果等价且可完整测试 |
| FTS 内容表 | 外部内容表 `content=''` | FTS5 普通虚拟表 | 外部内容表需手写严格对齐的触发器，易错难调试；索引是可抛弃缓存，多存一份正文可接受 |
| WebView2 兜底 | 未指定 | 注册表探测 + `mshta` 原生弹窗 | `MessageBoxW` 需引入 `windows-sys` 并写 unsafe，与 `unsafe_code="forbid"` 冲突 |
| IPC 类型 | tauri-specta 生成 | 手写类型与命令一一对应 | 本轮先稳定接口，接入代码生成属后续优化 |

**这些偏离都不改变对外行为。**

## 七、需要你决策的事

### 1. PDF 导出（计划书标注的最高风险项）

本轮做了设计与风险拆解，写进 [pdf-spike.md](./pdf-spike.md)，
但**没有做实际验证**。核心问题：

- 首选方案（WebView 打印到 PDF）需要写**三份平台特定 FFI 代码**，
  且要求 WebView 已创建 —— 与「导出不依赖 UI」的设计有冲突
- 备用方案（纯 Rust 渲染）中，Typst 体积通常 >10 MB，
  **会吃掉为内置字体预留的安装包预算**

**需要你决定**：若 macOS/Linux 上首选方案不可行，
是接受安装包变大，还是「Windows 优先做 PDF、其它平台暂缓」？

### 2. 下一轮的优先级

按对「能用」这一目标的影响，我建议的顺序是：

1. **编辑器内核（M4）** —— 写作软件的核心，没有它「打开即写」不成立
2. **统计与检索的前端界面（M6 / M8）** —— 数据层已完备，只差接线
3. **PDF 导出 Spike** —— 单独安排，避免阻塞其余五种格式
4. **字体子集化流水线** —— 阻塞内置字体与安装包体积验收

如果你有不同判断，请告诉我。

## 八、诚实说明：哪些没做完

计划书是 17–18 周、11 个里程碑的完整体量。本轮完成了其中
**「工程骨架 + 数据底座 + 界面基座」** 这一块，具体是：

- **完成**：M0、M1、M2（除 Should 项）、M3
- **数据层完成、界面未接**：M7 导出、M8 统计、M6 检索
- **部分完成**：M5 书架与卷章管理、M9 外观设置
- **未开始**：M4 编辑器内核、M11 性能验收

**「能用」这一阶段目标尚未达成** —— 因为最关键的编辑器内核还没做。
但底座是扎实的：数据安全机制（原子写 / 备份 / 崩溃恢复 / 回收站 /
冲突识别）已由 335+ 个测试覆盖，这部分返工风险最低，
后续所有功能都可以建在它上面。
