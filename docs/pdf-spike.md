# PDF 导出 Spike 结论（T0.14 / R16）

> **风险编号**：R16 —— 计划书中标注为「v1.2 新增，最大技术不确定项」。
> **文档版本**：v1
> **状态**：**未完成实测，仅有设计与可行性分析。**
> 本文件诚实标注这一点，不把「设计上可行」写成「已验证」。

## 为什么这个问题重要

PDF 是六种导出格式中**唯一需要嵌入中文字体子集**的格式
（计划书 9.1 节能力矩阵：PDF 列「必须嵌入子集」）。
同时它也是唯一没有纯 Rust 轻量实现路径的格式 ——
其它五种格式都可以用 `pulldown-cmark` + `zip` 两个依赖覆盖，
而 PDF 需要一个完整的排版与字体嵌入引擎。

计划书给出的首选方案是**复用系统 WebView 的「打印到 PDF」能力**：
从生成的打印就绪 HTML 直接出 PDF。

## 首选方案：WebView 打印到 PDF

### 为什么选它

| 优点             | 说明                                                     |
| ---------------- | -------------------------------------------------------- |
| 零额外依赖       | 不引入 `printpdf` / Typst 等重型库，二进制体积不增加     |
| 与所见即所得一致 | 导出结果与用户在应用内看到的排版一致                     |
| 字体随渲染器嵌入 | 中文字体由渲染器处理，**文本可搜索、可复制**（P10 要求） |
| 分页由引擎处理   | 不需要自己实现分页算法                                   |

### 各平台实现路径

| 平台    | 引擎                 | 接口                          | 把握                                                        |
| ------- | -------------------- | ----------------------------- | ----------------------------------------------------------- |
| Windows | WebView2（Chromium） | `ICoreWebView2_7::PrintToPdf` | **较高**：Chromium 的打印能力成熟，接口稳定                 |
| macOS   | WKWebView            | `createPDF`（macOS 11+）      | 中等：API 存在，但与 Windows 的分页行为有差异               |
| Linux   | WebKitGTK            | `webkit_print_operation_*`    | **较低**：WebKitGTK 版本差异大，打印 API 在各发行版间不统一 |

### 关键风险

1. **Tauri 2 未直接暴露该能力**
   Tauri 的 WebView 抽象层没有提供「打印到 PDF」的跨平台封装。
   要实现需要写**平台特定绑定**：
   - Windows：通过 `webview2-com` 拿到 `ICoreWebView2` 接口
   - macOS：通过 objc2 调用 `WKWebView.createPDF`
   - Linux：通过 `webkit2gtk` 的 C API

   这意味着**三份平台特定代码**，且都需要 `unsafe`
   或至少需要与 `unsafe` 的 FFI 打交道 —— 这在
   `unsafe_code = "forbid"` 的工作区约定下需要单独决策。

2. **该能力要求 WebView 已创建并有真实页面**
   导出 PDF 需要先渲染一个隐藏窗口。这与「导出不依赖 UI」的设计
   有冲突，也让导出难以在无头环境（CI）中测试。

3. **分页控制粒度有限**
   计划书允许「卷首分页」，但 WebView 打印对分页位置的控制
   依赖 CSS `page-break-*`，精细控制能力弱于专业排版引擎。

## 备用方案：纯 Rust PDF 渲染

若首选方案在某平台不可行，计划书列出 `printpdf` 或 Typst 库作为退路。

| 方案            | 体积代价                            | 中文支持                     | 排版质量                     |
| --------------- | ----------------------------------- | ---------------------------- | ---------------------------- |
| `printpdf`      | 中等（含字体子集嵌入逻辑）          | 需自行处理字体子集与字形映射 | 需自己实现换行、分页、避头尾 |
| Typst（作为库） | **大**（完整排版引擎，通常 >10 MB） | 良好                         | 优秀                         |

**核心矛盾**：这与安装包预算 P6（≤ 25 MB）直接冲突。
Typst 的体积会吃掉为内置字体预留的预算。

**中间路线**：`printpdf` + 自行实现最小排版（左对齐、固定行距、
按字数或按行分页）。工作量不小，但可控，且不引入大型依赖。

## 当前状态与本轮结论

### 已具备的前提

- **打印就绪 HTML 的生成能力已实现**（M7 的 HTML 渲染器），
  这是首选方案的输入，已经就绪。
- 样式已按打印场景设计（响应式、正文最大宽度、行高 1.8）。

### 尚未做的验证

**本 Spike 未完成实际验证。** 具体来说：

1. 未在 Windows 上写出 `PrintToPdf` 的调用代码
2. 未实测中文是否被正确嵌入（P10 的核心要求）
3. 未评估 macOS / Linux 的可行性
4. 未测量三平台的分页行为差异

### 建议的验证步骤（下一轮执行）

1. **最小验证**：在 Windows 上创建一个隐藏 WebView2，
   加载一段含中文的 HTML，调用 `PrintToPdf`，用文本选择确认
   「中文可复制」这一硬性要求
2. **体积测量**：记录该实现引入的额外二进制体积（预期接近 0，
   因为 WebView2 是系统组件）
3. **备选路径评估**：若 Windows 成功但 macOS/Linux 受阻，
   评估「Windows 用 WebView 打印 + 其它平台用 `printpdf`」
   这种混合方案的维护成本
4. **决策点**：向用户确认 —— 若引入纯 Rust 排版导致二进制体积
   显著增加，是否接受（这是计划书 17 节列出的待确认问题之一）

## 对排期的建议

计划书把 PDF 排在其他格式之后实现，这是正确的。
本轮的实际进展也印证了这一点：

- TXT / Markdown / HTML / EPUB 都不需要额外依赖，已可推进
- DOCX 只需手写 OOXML + `zip`，已可推进
- **PDF 是唯一可能改变依赖策略与体积预算的一项**

因此建议：**先让其余五种格式达到可用并完成验证，
再单独为 PDF 安排一个 Spike 迭代**，避免它阻塞整条导出线。

## 给用户的问题

以下问题需要你的决策（计划书 17 节列出的待确认项）：

1. 若 PDF 的首选方案在 macOS/Linux 不可行，是否接受引入纯 Rust
   渲染带来的二进制体积增加？这会与安装包 ≤ 25 MB 的预算冲突。
2. 若必须取舍，是「Windows 优先做 PDF、其它平台暂缓」，
   还是「三平台都做，接受安装包变大」？
